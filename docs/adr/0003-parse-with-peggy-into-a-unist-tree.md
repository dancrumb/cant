# 0003. Parse with Peggy into a unist syntax tree

- **Status:** Accepted
- **Date:** 2026-11-14

## Context

Cant needs a parser that turns source into a syntax tree for the compiler, interpreter and language server to work from. The language is young and its syntax will change often, so the parser needs to be easy to change. The language server needs to know where every node is in the source. Cant source is also written inside Markdown, which is already handled with unified and its unist trees (see `weave` and the VS Code extension).

## Decision

- The grammar is written for [Peggy](https://peggyjs.org/) in `packages/shared/src/cant.peggy`.
- The parser builds a [unist](https://github.com/syntax-tree/unist) tree using `unist-builder`. Every node has a unist `position`. Tokens from the tokenizer use the same `Position` type.
- Statements are held in a node's `children`. Other sub-nodes, such as an action's name or a call's arguments, are held in named fields.
- The parser is generated by a turbo `generate` task into `src/generated/`, which is not committed. `parse.ts` is the typed entry point, and `ast.ts` defines the node types.

## Consequences

- Changing the syntax means editing a grammar, not hand-written parsing code.
- Cant trees share position types and conventions with the Markdown trees, and unist utilities can be used on them.
- Because only statements are in `children`, `unist-util-visit` and similar utilities walk statements but not the expressions and identifiers inside them. Code that needs to reach those has to follow the named fields.
- The node types in `ast.ts` are kept in step with the grammar by hand, and the tests are what catches a mismatch.
- The generated parser is JavaScript, so `cant-shared` builds with `allowJs`, and the build, typecheck and lint tasks all depend on `generate`.
